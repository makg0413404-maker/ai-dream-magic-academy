## 一、產品定位（品牌世界觀統一命名）

AI 圓夢魔法學院不是一個提示詞網站，而是一個 **AI 魔法咒語平台**。

### 1.1 品牌世界觀命名對照

| 魔法世界命名 | 產品含義 | 技術對應 |
|:------------|:---------|:---------|
| **AI 圓夢魔法學院** | 品牌整體 | 整個產品 |
| **魔法圖書館（Magic Library）** | 提示詞模板、行業知識、範例的總集 | 知識庫 + 模板庫 |
| **魔法咒語（Magic Spell）** | 最終產出的可複製提示詞 | Spell Engine 輸出 |
| **我的魔法書（My Spellbook）** | 會員收藏/歷史咒語 | 會員中心子頁 |
| **AI 魔法顧問（AI Magic Advisor）** | 引導使用者填寫需求的 Agent | Agent（Coze / LLM） |

✅ 所有命名以「魔法」為主體意象，與品牌世界觀一致。
✅ 不使用「Prompt Generator / 提示詞產生器」等工程名稱。

## 二、核心架構（Magic Spell Engine）

### 2.1 高層資料流

```
使用者
  │
  ▼
AI 魔法顧問（Agent）
  │  分析：行業、客群、行銷目的、內容形式、風格、使用工具
  │  輸出：統一結構化資料（Spell Request）
  │
  ▼
Magic Spell Engine（咒語引擎）
  │  輸入：結構化資料
  │  處理：行業知識 + 模板 + 規則 + 變數動態組合
  │  輸出：完整魔法咒語（中文，含角色/任務/風格/細節/輸出格式）
  │
  ├──→ ChatGPT / Gemini（文字工具）
  ├──→ 即夢（圖片工具）
  └──→ 豆包（影片工具）
```

### 2.2 命名的哲學：為什麼用「統一引擎 + 知識庫」而非「大量工作流」？

**問題**：如果為每個行業（餐飲/零售/教育/美容/醫療…）各自建立一套 Coze 工作流，系統會：

- ❌ 隨行業成長線性擴充 → 100 行業 = 100 套工作流
- ❌ 每套獨立法則 → 難以共用優化
- ❌ 維護成本爆發
- ❌ 新行業需開發，非配置

**解決方案**：建立一套統一引擎，用 **知識 + 模板 + 規則** 來動態組合。新行業只需要「新增知識庫條目 + 調參數」，不需要新增工作流。

## 三、AI 魔法顧問的職責

### 3.1 顧問的工作（不做直接生成咒語）

AI 魔法顧問（Agent）的職責**不是直接生成魔法咒語**，而是**收集並標準化使用者需求**，輸出統一結構化資料。

**輸入**（來自使用者回答的簡單問題，≤ 5 個問題）：

| 問題 | 選項範例 |
|:----|:---------|
| 你的行業是什麼？ | 餐飲 / 零售 / 教育 / 美容 / 個人品牌 / 醫療 / 其他 |
| 你想做什麼內容？ | 圖片 / 影片 / 文案 / 廣告 / 社群貼文 |
| 你的目標是什麼？ | 引流 / 品牌曝光 / 促銷 / 教育客戶 / 個人介紹 |
| 你的客群是誰？ | 年輕女性 / 家庭主婦 / 熟齡 / 上班族 / 創業者 |
| 你使用的 AI 工具？ | ChatGPT / 即夢 / 豆包 / Gemini / 通用 |

**輸出：Spell Request（統一結構化 JSON）**

```json
{
  "industry": "餐飲",
  "content_type": "圖片",
  "goal": "品牌曝光",
  "audience": "家庭主婦",
  "style": "溫暖、生活感",
  "platform": "即夢",
  "tone": "親切、說人話",
  "length_hint": "1 張圖片 + 3 句文案",
  "extra_notes": "主打媽媽的味道"
}
```

### 3.2 為什麼不直接在 Coze 生成咒語？

- ✅ 結構化資料獨立於輸出格式 → 一個結構可產生多種咒語
- ✅ 減少 Coze 複雜度 → Coze 只做組合，不做分析
- ✅ 便於未來擴充 → 新行業只需更新知識庫，不需改 Agent 邏輯

### 3.3 AI 魔法顧問的實作方式（MVP 階段）

**MVP（第一版）**：純前端表單（類似目前的提示詞工具），使用者自己填選項，直接輸出 Spell Request JSON（隱藏，不做 Agent）。

**第二階段**：接入 Coze/LLM Agent，使用者用自然語言描述需求，Agent 自動解析成 Spell Request。

## 四、Magic Spell Engine 的職責

### 4.1 核心設計原則

> **不要依照不同行業建立不同工作流。利用：行業知識 + 模板 + 規則 + AI 動態組合。**

```
Spell Request（結構化資料）
  │
  ▼
┌─────────────────────────────────────┐
│         Magic Spell Engine          │
│                                     │
│  1. 知識比對層                       │
│     - 讀取該行業的知識庫條目         │
│     - 讀取該內容類型的規則           │
│                                     │
│  2. 模板選擇層                       │
│     - 根據 content_type + goal       │
│     - 選取對應咒語範本              │
│     (所有行業共用同一套範本，         │
│      變數由知識庫填充)               │
│                                     │
│  3. 變數填充層                       │
│     - 行業關鍵詞 → 填充關鍵變數     │
│     - 風格/語氣/平台 → 對應修飾詞   │
│     - 目標 audience → 調整語氣      │
│                                     │
│  4. 組合輸出層                       │
│     - 模板 + 變數 → 完整咒語        │
│     - 支援多平台輸出變體            │
│                                     │
└─────────────────────────────────────┘
  │
  ▼
完整魔法咒語（中文，可直接複製使用）
```

### 4.2 模板的組織方式（通用化）

**不要為每個行業建立獨立模板**。模板只依 **內容類型** + **輸出格式** 區分：

| 模板 ID | 內容類型 | 輸出格式 | 範例用途 |
|:--------|:---------|:---------|:---------|
| img-01 | 圖片 | 通用繪圖 | 任何行業的 AI 圖片生成 |
| img-02 | 圖片 | 即夢專用 | 針對即夢工具優化 |
| vid-01 | 影片 | 通用腳本 | 任何行業的影片腳本 |
| vid-02 | 影片 | 豆包分身 | 針對分身影片優化 |
| copy-01 | 文案 | 社群貼文 | 任何行業的社群文案 |
| copy-02 | 文案 | 廣告文案 | 任何行業的廣告稿 |
| ad-01 | 廣告 | 影片腳本 | 廣告行銷影片 |

**行業差異只由「知識庫」管理**（變數填充層），不影響模板結構。

### 4.3 實作方式（分階段）

**MVP（第一版）**：
- 純前端 JS + 模板字串組合（沿用現有提示詞工具架構）
- 3 種內容類型（繪圖/分身影片/廣告），共用模板
- 行業知識庫：硬編碼在 JS 物件中（20–30 行業）
- 不需要 Coze、不需要後端

**第二階段**：
- 將知識庫移到 JSON / Markdown 檔案（可編輯，不需重新部署）
- Magic Spell Engine 搬到後端 API（Next.js API Route）
- 接入 Coze 核心工作流處理更複雜的組合邏輯

**第三階段**：
- 知識庫升級為正式資料庫（Supabase）
- AI 魔法顧問接入 LLM Agent 自動解析自然語言
- 模板支援 A/B Test + 使用者回饋自動優化

## 五、Coze 工作流分析

### 5.1 Coze 應負責的工作

| 工作 | 原因 |
|:----|:-----|
| **Spell Request 生成**（第二階段起） | 接收自然語言→結構化，LLM 擅長 |
| **複雜咒語優化** | 同時考慮多個行業交叉規則時 |
| **品質檢查 / Spell Lint** | 檢查咒語是否有衝突/不合理 |
| **使用量分析與回饋** | 記錄生成成功率、複製率 |

### 5.2 Coze 不應負責的工作

| 工作 | 原因 | 替代方案 |
|:----|:-----|:---------|
| **模板維護** | 模板應由產品團隊直接編輯，非流程控管 | Markdown / JSON / 資料庫 |
| **行業知識庫查詢** | 查表比跑 Coze 流程快 100 倍、穩定 100 倍 | 前端 JS Map / 後端 DB 查詢 |
| **變數填充** | 純文字組合，不需 LLM | JS 模板字串 |
| **輸出格式轉換** | 固定規則，不須 Agent | 前端或輕量後端 |
| **最終檢查/複製按鈕** | UX 功能，非流程 | 前端元件 |

### 5.3 設計原則

```
儘量
  知識庫 → 本地資料（JSON/DB）
  模板 → 本地或 Git 託管
  組合 → 輕量後端或前端
  ────
只在需要 LLM 時才用 Coze
```

## 七、未來擴充規劃（共用核心架構）

### 7.1 擴充原則

> **全部共用同一套核心架構，不重新建立系統。**

| 未來顧問 | 與核心架構的關係 |
|:---------|:----------------|
| AI 創業顧問 | 使用相同的 Spell Request 結構 + 行業知識庫（創業相關行業） |
| AI 行銷顧問 | 使用相同的 + 行銷架構知識庫 |
| AI 八字顧問 | 新知識庫（命理）+ 新模板（命理咒語）但仍用 Magic Spell Engine |
| AI 紫微顧問 | 同上 |
| AI 塔羅顧問 | 同上 |

### 7.2 擴充流程

```
新顧問類型
  │
  ▼
1. 新增知識庫條目（不用改程式）
2. 新增咒語模板（1–3 個）
3. 註冊到 AI 魔法顧問路由
  │
  ▼
即可上線！（不需新工作流、不需新引擎）
```

## 十、CTO 評估

### 10.1 是否能支撐 100+ 行業、1000+ 魔法咒語？

**可以**。原因：

1. **行業獨立於工作流**：100 行業 = 100 條知識庫條目 + 0 條新工作流
2. **模板通用化**：8–15 個通用模板即可涵蓋 90% 內容類型（圖片/影片/文案/廣告/社群），行業差異由變數填充
3. **組合而非分類**：不為「餐飲×圖片×即夢」建立獨立工作流，而是「圖片模板 + 餐飲知識 + 即夢變數」動態組合
4. **1000 咒語 = 1000 筆知識庫記錄 + 15 模板 × 3 變體，不是 1000 套工作流**

### 10.2 主要技術風險與預防

| 風險 | 影響 | 預防 |
|:----|:-----|:-----|
| **Spell Request 結構化失敗** | Coze Agent 輸出格式錯誤，引擎無法讀取 | 強型別檢查 + 預設值 + 複數次重試 |
| **知識庫品質不穩** | 輸出咒語品質因行業不同差距大 | 標準化知識庫欄位 + 人工審核上線 |
| **輸出品質不一致** | 「好像會用但又不夠好」→ 使用者失望 | MVP 階段人工維護模板；第二階段前不做 Coze 直接輸出 |
| **Coze 穩定性 / 延遲** | 現場展示時 Coze 掛掉或慢 | Coze 只用於 Agent（非即時），引擎為純組合（無 LLM）、毫秒級回應 |
| **咒語太長/太短** | 使用者覺得不實用 | 模板長度限制 + 可編輯後複製 |

### 10.3 CTO 建議

1. **先跑完剩餘的 8/3 展示流程**（報名/加入）再進入 Magic Spell Engine 第二階段。
2. **提示詞工具 MVP 已經符合「統一引擎」精神**——三個內容類型共用同一套組合邏輯，不是各自獨立的工作流。這是正確的方向，應以此為核心擴充知識庫與模板數量，而不是新增工作流。
3. **知識庫應盡早從硬編碼搬到 JSON**（最簡單的檔案層級），讓產品團隊可以獨立編輯行業內容，不依賴開發者。
4. **不要在 MVP 就接 Coze**——風險高、成本高、展示不穩定。模板組合即可應付 8/3 展示。
5. **每階段只加一個複雜度**：MVP = 本地組合 → 第二階段 = 知識庫檔案 + 後端 API → 第三階段 = Coze + 資料庫。一次加太多會爆。
